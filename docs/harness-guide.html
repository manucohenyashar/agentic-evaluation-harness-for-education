The idea

What a harness is, in one sentence

Definition

A harness is a program that runs your whole system end to end on inputs you control, and scores whether the answer was right.

That is the entire idea. It is not a framework and not something you install. Three things follow from it, and they are what make it worth having:

  • Whole system, not one function. A unit test proves one piece works. A harness proves the pieces combined produce the right answer. Your system has nineteen modules handing work to each other; every one can be individually correct and the final grade still wrong.
  • Inputs you control. Real student PDFs vary. The harness runs a fixed set where you already know the right grade, so a difference in output means the code changed — not the data.
  • It scores the outcome. Not “did it finish without crashing” but “was the grade right, and did it avoid the specific wrong answers we care about.”

Advisor360 built this because ViDA merged 450+ agent-written pull requests in under a month with no regressions. The harness is what made that safe. It is not overhead that slows you down; it is what lets you change code fast without fear.

The mental model

The ladder

Test lanes, from cheap and fast to slow and real. Each rung catches a class of bug the rung below cannot. Build the bottom one first — a green top rung sitting on an unproven bottom tells you almost nothing.

L0
Offline — pure logic, no model
Functions with no input or output of any kind: band aggregation, the confidence inversion, grade policy, span verification, prompt assembly. Your design already declares all six of these pure, which is why this rung is unusually large here — most of the risky logic needs no model at all.
secondsevery commitblocks merge
L1
Component & contract
Each module checked against its CT-* contract clauses, plus the same cases run against every test double. Your test plan already generates these.
secondsevery commit
L2
Integrated local bring-up
The whole pipeline on one synthetic cohort, with every model call served from recorded fixtures. No network, fully deterministic.
~1 minevery PR
L3
End to end on the synthetic corpus
Ingest → extract → integrity → judge → aggregate → grade, against a real local model, scored against grades you already know.
~10–30 minon behaviour change
L4
Nightly conformance
The frozen fixture set through both backends, comparing where they diverge. You have already designed this as a module — it is M‑CONFORM.
~1 hrnightly
← cheap · fast · deterministicexpensive · slow · real →
The good news

Your design is already harness-shaped

The bootstrap playbook says to design four seams in on day one, because they are painful to add later. All four are already in your detailed design — written before anyone read the harness docs. Adoption is mostly naming what exists.

Seam the harness asks forAlready in your design asClause
A headless driverThe orchestrator's create_run / start / progress. The console is explicitly optional — killing it does not affect a run.CT-ORCH-01
A deterministic transport for every dependencyThe recorded-fixture provider: keyed by a hash of the assembled request, raises rather than touching the network.CT-PROV-10
Env-gated knobs for every environment-sensitive constantEvery module has a Configuration section; the run config freezes about twenty named knobs into one immutable value.CT-CONF-11
Stage-level observability in the resultRun metrics, per-gate ingest outcomes (deliberately not collapsed to a boolean), progress reports, integrity signals.CT-INGEST-08

The same holds for the harder ideas. Score the outcome, not the route is your paired benign-twin fixtures. Metamorphic relations are your order-permutation and replication requirements. Flake-aware gating is already implied by the clause that states outright that verdicts are not reproducible.

The corpus is the one to plan around. The Confluence page is blunt about it: “the domain corpus is the expensive part of the whole build, because there is no generic synthetic-data generator to reuse.” Start with three submissions, not fifty — you will build the wrong fifty.

The gap worth closing

The kit sets a bar your pipeline does not: deliberately introduce a bug anywhere in the core behaviour, and something must go red. Coverage cannot tell you this; mutation testing can.

It matters unusually much here, because so much of your design is negative — no numeral in a judge prompt, no path from empty evidence to a low band, no even panel. A test that fails to catch one of those violations looks identical to one that does. mutmut is the Python equivalent; scope it to the pure-function modules first, where it is cheapest and means the most.

3

Build the bottom rung with the first module

Start where your dependency graph says to: the run config or the persistence substrate. When you implement the module, implement its L0 tests in the same change. That is the whole discipline.

4

Turn the verification gate on

Once the first tests exist, set TEST_CMD in .claude/settings.json so no session can end claiming success without a green suite.

{ "env": { "TEST_CMD": "uv run pytest -m \"not slow\"" } }
5

Add the runner when there are two stages to connect

Once the orchestrator and one worker exist, add harness/cli.py with run and batch. Not before — a runner with nothing to run is scaffolding.

6

Grow the corpus incrementally

Three synthetic submissions, then grow. Every bug anyone finds later becomes a permanent case, so the set only ever tightens.

The one habit

When you add a feature, add its harness case in the same change.

Not next sprint, not “when we get to testing” — the same change. That single habit is the difference between 450 pull requests with zero regressions and a harness that permanently lags the code as an afterthought. Your design already gives you the hooks: every FR-* says what must be true, every CT-* says what callers may rely on, and the traceability checker fails the build when either has no test.
